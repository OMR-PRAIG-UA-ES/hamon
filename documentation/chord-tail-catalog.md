# Chord-tail catalog

What real corpora put in a chord-symbol tail that HAMON does **not** interpret.
Generated by `tools/scripts/chord_tail_catalog.py` from the datasets under
`datasets/_data/`; only counts and vocabulary are kept, never the data. Regenerate it
after changing the chord-tail vocabulary.

A tail part is *unread* when nothing in the normalizer interprets it. Before issue #5 an
unread word was dropped and the label still came out as an ordinary chord.

## Coverage

| Source | Labels | Distinct | Kept as text | With an unread part |
|---|---:|---:|---:|---:|
| `choro` | 44067 | 682 | 0 | 0 |
| `jazz-harmony-treebank` | 59150 | 181 | 0 | 0 |
| `mcgill-billboard` | 113780 | 975 | 0 | 0 |

## Unread parts

None: every part of every chord tail in these sources is interpreted.

## What the first run found (2026-10-14)

The catalog was built to settle issue #5 (what to do with a word HAMON does not
understand). Run over the sources above it found **no unknown word** in any chord tail, so
the rule "a tail with an unread word stays text" costs these corpora nothing. What it found
instead were three things that *were* being dropped, none of them a word:

| Found | Where | What was wrong | Fixed |
|---|---|---|---|
| `%` | `jazz-harmony-treebank`, 2385 chords (`D%7`) | The treebank's own half-diminished sigil (its readme); the adapter only knew iReal's `h`, so the chord read as a plain dominant seventh. | `%` → `ø` |
| `(4)` | `choro`, 205 chords (`G7(4)`) | A plain 4 had no meaning, so it vanished. | read as an added fourth |
| `7M` | `choro`, 35 distinct chords (`Bb7M`) | Not HAMON syntax; the Choro adapter already rewrites it to `maj7` (`normalize_chord`), which this catalog applies too. | already handled |

The Billboard Harte labels all read: after the degree-list work for issue #3 none is kept
as text (`sus4(b7)`, `1(b3)`, `maj9(13)`, … used to be cut at the comma).
