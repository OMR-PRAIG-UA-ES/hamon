# HAMON — Harmony Encoding Formats

HAMON — **Ha**rmony **Mo**del and **N**otation — is a universal harmony-label standard: a stable exchange layer that sits between music-encoding ecosystems. Everything hinges on one **canonical JSON structure** (`grammar/hamon-schema.json`): it is the normative hub, and every external format maps to and from it. As long as the source format is expressive enough, round-trips lose nothing.

The **EBNF grammar** (`grammar/hamon.ebnf`) is a compact text serialization of that JSON — a human-readable surface string like `CΔ7`, `V7`, or `6-5`. Think of it as one encoding of the JSON, not the hub itself.

This documentation walks through how each supported format encodes harmony, what it can and cannot represent, and how HAMON maps to and from it.

## Capability matrix — which format carries which system

The two axes are **orthogonal**: rows are the encodings and libraries, columns are the
harmony **systems** (and the key analytical aspects). A ✓ means the format can carry that
aspect **natively**. HAMON is the only one that carries them all — which is exactly why it
works as the interlingua.

| Format / library | Chord sym. | Roman | Fig. bass | Functional | Nashville | Applied | Key/region |
|---|:-:|:-:|:-:|:-:|:-:|:-:|:-:|
| **HAMON** (interlingua) | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| MEI | ✓ | – | ✓ | – | – | – | – |
| Humdrum | ✓ | ✓ | ✓ | ✓ | – | ✓ | ✓ |
| MusicXML | ✓ | ✓ | – | – | – | – | – |
| Dezrann | – | – | – | – | – | – | – |
| DCML | – | ✓ | – | – | – | ✓ | ✓ |
| RomanText | – | ✓ | – | – | – | ✓ | ✓ |
| Harte · iReal Pro | ✓ | – | – | – | – | – | – |
| JAMS | ✓ | – | – | – | – | – | ✓ |
| LilyPond · ABC · MuseScore | ✓ | – | – | – | – | – | – |
| music21 · partitura · FlexOHR *(library)* | ✓ | ✓ | – | – | – | – | – |
| ms3 *(library)* | – | ✓ | – | – | – | ✓ | ✓ |

> **Nashville numbers, chord-scales and non-harmonic tones are HAMON-only** — no source
> format encodes them natively, so HAMON is what lets them travel. DCML / RomanText express
> tensions and inversions *on the Roman numeral* rather than as a bare chord symbol, hence
> the empty *Chord sym.* cell. **Text does not count**: MEI's `<harm>` and Dezrann's `tag`
> accept any string, so a Roman numeral parked there is carried as our text, not encoded —
> that is why MEI is credited only with figured bass and chord symbols, and Dezrann with
> nothing structured. The format rows are rendered from the capability model in
> [`../hamonpy/hamonpy/capability.py`](../hamonpy/hamonpy/capability.py) (the same table
> behind the ICCCM'26 loss matrix and the site; `test_capability.py` fails if this file
> drifts from it) — **provisional, to be validated with Johannes / Fabian**. The library
> rows are hand-kept.

## Harmonic analysis (v0.2.0)

Labeling individual chords is only part of the story. HAMON v0.2.0 adds an optional
**analytical layer** for a full harmonic analysis: tonal regions and modulations,
tonicizations, secondary dominants / dominant-of-the-dominant, layered functional
analysis (key / function / degree / bass), note-level melodic analysis of harmonic and
non-harmonic tones (passing, neighbor, suspension, appoggiatura, *nota cambiata*, …),
modal harmony (church modes), omitted fundamentals, chord arpeggiation/unfolding, and
alternative whole-progression readings. Every analytical field is optional, and older
0.1.0 documents keep working unchanged.

See **[Analytical layer (analysis.md)](analysis.md)** for the full specification,
and **[Berklee-style jazz analysis & the MuRET-hamon pipeline (berklee-jazz.md)](berklee-jazz.md)**
for the jazz/Berklee encoding and the HAMON-as-interchange workflow
(JAZZMUS → HAMON → MuRET-engraving / Dezrann).

Two focused notes cover concerns that cut across everything else:

- **[Time-aligned positions (positions.md)](positions.md)** — how measures, beats and audio
  seconds are encoded (`m:1,ts:3`, `t:5/4`, `s:12.34`, `ref:id`) in the surface and JSON, why
  the clocks coexist instead of converting, and why HAMON anchors labels without modelling
  durations.
- **[Systems, the `@` hint, and the analytical layer (systems.md)](systems.md)** — why
  `@cs` is still correct for a label carrying `[of:II]`/`[scale:…]`, and when to reach for
  `@auto` instead.

## Datasets & use cases (the harmony hub)

HAMON converts real corpora into the canonical model, but it **does not bundle**
third-party datasets. Instead it ships a registry of the original sources (authors,
license, citation, URL) plus a small downloader (`hamonpy.datasets`). You fetch each
corpus from its authors, then convert it with a format adapter.

- **[Datasets (datasets.md)](datasets.md)** — the registry, download policy, and API.
- **[`use-cases/`](../use-cases/README.md)** — worked, runnable recipes.
- **[CLI (cli.md)](cli.md)** — `hamon convert <file>` (any format → canonical JSON) and `hamon datasets …`.

## The HAMON JSON specification

`grammar/hamon-schema.json` is a **JSON Schema 2020-12** document, and it is the normative hub of the standard. Every other encoding is described as a mapping to and from it.

### Structure at a glance

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id":     "https://hamon.music/schema/hamon-sequence.json",
  "version": "0.1.0",
  "$ref":    "#/$defs/HamonSequence",
  "$defs": {
    "HamonSequence":  { ... },
    "HarmonyGroup":   { ... },
    "HarmonyLabel":   { ... },
    "HarmonySemantic": { "oneOf": [ ... ] },
    "ChordSymbolSemantic": { ... },
    "RomanSemantic":      { ... },
    "NashvilleSemantic":  { ... },
    "FiguredBassSemantic":{ ... },
    "FunctionalSemantic": { ... },
    "NoChordSemantic":    { ... },
    "TextSemantic":       { ... },
    ...
  }
}
```

### Key design decisions

| Schema feature | Choice | Reason |
|---|---|---|
| Meta-schema | JSON Schema 2020-12 | Latest stable draft; `unevaluatedProperties` support |
| Top-level type | `HamonSequence` via `$ref` | Single root object; all definitions are `$defs` |
| Semantic union | `HarmonySemantic` as `oneOf` discriminated by `"kind"` | Maps 1-to-1 to the typed AST union in `hamonpy/ast.py` |
| Surface string | Required field on `HarmonyLabel` | Round-trip fidelity — exact original glyphs always preserved |
| `additionalProperties: false` | On every object | Strict schema; implementations catch unknown fields early |
| Versioning | `"version": "0.1.0"` top-level field (semver) | MAJOR = breaking, MINOR = new optional fields, PATCH = descriptions |

### The discriminated union

`HarmonySemantic` is a `oneOf` with seven variants. A literal `"kind"` field identifies which one you have:

| `kind` | Covers | Typical surface |
|---|---|---|
| `chordSymbol` | Chord symbols | `CΔ7`, `Am7`, `Bb`, `G7/B` |
| `roman` | Roman numerals | `I`, `bVII`, `V7/IV` |
| `nashville` | Nashville numbers | `1`, `4m`, `b7` |
| `figuredBass` | Figured bass | `6-5`, `4-3` |
| `functional` | Functional harmony | `T`, `DD`, `PD->T` |
| `noChord` | No-chord indicator | `N.C.`, `NC` |
| `text` | Unrecognized / free text | anything else |

### Reading the schema

- All reusable types live in `$defs`; follow `$ref` to navigate between them.
- `HarmonyLabel.semantic` is the parsed output; `HarmonyLabel.surface` always holds the original glyph string.
- `HarmonyGroup.position` (schema 0.2.1, optional) carries a time-aligned position when the label comes from a positioned format — `measure`+`beat` (MEI `@tstamp`), an absolute `time` fraction, or a `ref` (MEI `@startid`).
- `RenderingHints` (`qualityGlyph`, `seventhGlyph`, `accidentalGlyphs`) record display variants. That is how `CΔ7`, `CM7`, and `Cmaj7` all normalize to the same semantic yet round-trip back to their original surface.
- The full changelog lives in `CHANGELOG.md` at the repo root.

## The HAMON grammar as the exchange hub

The grammar (`grammar/hamon.ebnf`) defines five harmony systems plus two structural types:

| System | `systemId` | Examples |
|---|---|---|
| Chord symbols | `cs` | `CΔ7`, `Cm7`, `Bb`, `G7(#11)/D` |
| Roman numerals | `rn` | `I`, `bVII`, `V7/IV`, `#iv°7` |
| Nashville numbers | `ns` | `1`, `4m`, `b7`, `5/7` |
| Figured bass | `fb` | `6-5`, `4-3`, `7-6` |
| Functional | `fun` | `T`, `S`, `D`, `DD` |
| No chord | — | `N.C.`, `NC` |
| Text (lossless fallback) | `text` | any unrecognized label |

A `HamonSequence` can carry an optional `@<systemId>` hint to disambiguate tokens that could belong to more than one system. For example, `4` reads as Nashville under `@ns`, but without that context it could just as easily be a figured-bass numeral.

## Cross-format mapping summary

The tables below show which HAMON concepts each format represents natively. "✅" = a dedicated element or field; "text" = stored as a plain string (parseable but not structured); "❌" = not representable.

### Notation file formats

| HAMON concept | MusicXML | MEI | Humdrum | LilyPond | ABC | MuseScore | MNX |
|---|---|---|---|---|---|---|---|
| Chord symbol root | `<root-step>` | `@root` | `**mxhm`/`**jazz`/`**irb` | pitch name | quoted string | `<text>` | `root.step` |
| Chord quality | `<kind>` | `@quality` | spine token suffix | modifier | string suffix | `<text>` | `kind.value` |
| Major 7th glyph variant | `kind text=` | `@label` | token as-is | `majorSevenSymbol` | string as-is | `<text>` | `display` |
| Slash bass | `<bass>` | `@bass` | `/` in token | `/+pitch` | `/bass` | `<text>` | `bass.step` |
| Extension / alteration | `<degree>` | `@extens` | token suffix | modifier | string suffix | `<text>` | TBD |
| Roman numeral | text | `<harm>` text | `**harm` token | comment | comment | `<text>` | `roman-numeral` |
| Figured bass | text | `<fb><f>` | `**fb` / `**harm` | comment | comment | `<text>` | ❌ |
| Nashville number | text | text | `**harm` token | comment | comment | `<text>` | ❌ |
| Functional harmony | ❌ | text | `**function` token | comment | comment | `<text>` | ❌ |
| No chord | text | text | `.` (null) | — | — | `<text>` | TBD |
| Time position | `<offset>` | `@tstamp` | spine row order | note position | note position | element order | `position` |

### Third-party annotation formats

| HAMON concept | DCML TSV | Harte | iReal Pro | music21 |
|---|---|---|---|---|
| Chord symbol root | — | `Root` (e.g. `C`, `Ab`) | root note | `ChordSymbol.root` |
| Chord quality | `form` column | `Shorthand` (e.g. `maj`, `min`) | quality suffix | `ChordSymbol.chordKind` |
| Seventh | `figbass` column | shorthand (e.g. `maj7`, `7`) | quality suffix | `ChordSymbol.chordKind` |
| Suspension | — | shorthand (`sus4`, `sus2`) | `sus`/`sus4`/`sus2` | `ChordSymbol.chordKind` |
| Roman numeral | `numeral`+`form`+`figbass` | ❌ | ❌ | `RomanNumeral` |

| Prefix accidentals | `b`/`#` prefix on numeral | — | — | `frontAlterationString` |
| Secondary target | `relativeroot` | ❌ | ❌ | `secondaryRomanNumeral` |
| No chord | `@` rows (skipped) | `N` | `n`/`N` | `NoChord` |
| Time position | `mc`/`onset` columns | timestamp columns | bar structure | `offset` attribute |
